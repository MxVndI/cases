# B-UC-1.1: Авторизация через OAuth

**Эпик:** [Epic B1: Аутентификация и авторизация](../epics/epic-b01-auth.md)

## Описание

Авторизация пользователя через OAuth-провайдеров (Discord, Яндекс). Паролей нет — аутентификация только через внешних провайдеров или email-код.

## Акторы

- **Первичный:** Гость
- **Система:** Auth Service, User Service

## Предусловия

- Гость находится на странице входа
- OAuth-провайдер (Discord / Яндекс) доступен

## Основной сценарий

1. Гость нажимает кнопку OAuth-провайдера (Discord или Яндекс)
2. Фронтенд перенаправляет на `GET /{provider}/login` (provider: `discord` | `yandex`)
3. Auth Service формирует URL авторизации через `fastapi-sso` и перенаправляет гостя на страницу провайдера
4. Гость авторизуется у провайдера
5. Провайдер возвращает пользователя на `GET /auth/{provider}/callback` с кодом авторизации
6. Auth Service обменивает код на данные пользователя (email и т.д.)
7. Auth Service публикует RPC-запрос в Redis Streams (`user.rpc`) для получения/создания пользователя по email
8. User Service возвращает данные пользователя (id, email, nickname, role, status)
9. Auth Service создаёт сессию в MongoDB и кеширует в Redis
10. Auth Service подписывает session ID (HMAC-SHA256) и устанавливает cookie `sid` (срок жизни — 30 дней)
11. Пользователь перенаправляется на фронтенд (`/welcome`)

## Постусловия

- Пользователь авторизован
- Cookie `sid` установлен (HMAC-SHA256, TTL 30 дней)
- Сессия сохранена в MongoDB и закеширована в Redis
- Пользователь создан в User Service (если первый вход)

## Альтернативные сценарии

1. **Провайдер отклоняет авторизацию** → перенаправление на `/auth-error`
2. **User Service недоступен** (таймаут Redis Streams RPC) → сессия создаётся без данных пользователя
3. **Неподдерживаемый провайдер** → 404
